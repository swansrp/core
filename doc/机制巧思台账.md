# 机制巧思台账

> 定位：登记共享框架（`core/*`）中「巧思型」机制的设计动机与实测证据，防止后来者不知然否地改坏。
> 每条严格六要素：**问题 / 现有方案缺陷 / 本机制不变式 / 实测数字 / 可主张点 / 代价**。
> 实测数字口径：层 1 = 合成夹具（`ScriptedModel` 假模型 + `ContextProbeTools` 30k 中文报告 + `KEY-*` 深藏探针，确定可复现）；层 2 = 真模型四组对照（A 基线 / B 仅卸载 / C 仅预算 / D 双开）。

---

## 条目 1：工具结果入场卸载 + 句柄回捞（`toolResultOffloadChars` + `recallToolResult`）

- **问题**：多轮工具探索里，一条超大工具结果（如 30k 字的解析报告）全文进入消息窗口后，**每一轮后续请求都重付这笔 token**；滑动窗口只在驱逐时才摘要，救不了"还在窗内的每一轮"；模型输入爆炸且成本失控。
- **现有方案缺陷**：①条数窗口（`memoryWindow`）对"一条巨大结果"完全无感知——1 条 30k 与 1 条 50 字同计 1 条；②驱逐摘要（`digestOf`）发生在**被裁掉的那一刻**，此前每轮都已为全文付费；③若只做截断不留出处，模型丢信息后要么瞎猜要么重复调用原工具（同参重调在 `cachedTools` 下仍是全文照付）。
- **本机制不变式**：I1 配对完整（卸载只换文本不动结构）/ I2 顺序与类型不变 / I4 事件流全文是真源、回捞零损失 / I5 卸载必有取回路径（A10 起由框架两级通道保证：run 缓冲兜底 + 会话事件流优先，不再以链路能力位为前置）/ I6 钉住 ∪ askUser ∪ recallToolResult 永不卸载、回捞结果不二次卸载 / I7 句柄落在指针首行前 60 字符内，经任何 `brief` 截断仍可回捞 / I10 收口路径一律原文 / I15 摘要行内句柄与回捞工具注册同源（`recallUsable` 一布尔定生死，默认全关时二者皆无）。
- **实测数字**（层 1 合成夹具，`ToolAgentRunnerTokenBudgetTest#层1对照数字表`）：入窗峰值字符 **120100 → 24859**（D 组含三次回捞仍降 ~79%）；三处深藏探针 `KEY-A/B/C-8888`（位于 30k 原文 60% 偏移，头尾预览不可见）经句柄回捞**逐字符命中 3/3**；askUser 口径经钉住在末轮入窗存活；`cachedTools` 命中路径配新句柄可再回捞（`ToolAgentRunnerOffloadTest`）。层 2 真模型四组对照（peakReal、回捞真实调用分布、轮次变化）：`PENDING（缺：真模型四组对照，后置 InkHub 实测轮）`。
- **可主张点**：模型侧近零信息损失（可回捞、句柄可指针化再被摘要搬运仍完整）、人工侧零损失（事件流全文照旧、前端过程树可展开）；窗内指针被裁进摘要后句柄仍随行保留（I7 贯穿截断 + I15 贯穿驱逐，全程无失联点）；不新建表、不新建缓存、不新建端点——回捞只读现成会话事件流（I13 单写者不破）。
- **代价**：多一个内建工具 `recallToolResult` 进 specs（仅开启态注册，默认关零足迹）；Redis 写失败时事件流缺原文、跨 run 回捞可能落空（A10 起本 run 仍有缓冲兜底，返回"未找到句柄+可用清单"指令，模型按预览保守作答）；事件流存储量不因卸载下降（只压模型输入）；"何时必须回捞、何时预览够用"的判断责任落在提示词（指针尾行明令禁止凭预览猜测）；**摘要行每挂一个句柄多占约 30-40 字符**（真实 `tool_call_id` 长度），而摘要总长封顶 `DIGEST_MAX_LEN=3000`，故同容量下可留存的探索条数下降——换来的是被裁内容从"永久失联"变为"可按句柄取回"（I15）。

## 条目 2：裁窗计量单位从条数补上 token 预算（`contextTokenBudget`）

- **问题**：滑动窗口以「条」为唯一量纲，防的是消息**条数**堆积；但决定成本与端点上限的是 **token**——"20 条短消息"与"20 条含数万 token 大结果"获得同等待遇，既压不住爆炸也误伤精简长程探索。
- **现有方案缺陷**：①条数维度对 token 量纲两个方向都错（大结果占不满条数配额却撑爆上下文；小结果条数超了却远未到成本/上限）；②无估算回路则无从校准，真实 `inputTokenCount` 只在事后日志里出现。
- **本机制不变式**：I8 估算只高不低（CJK×1.0 + 其他×0.3 + 每消息 4 + 工具定义×1.2，宁高估早裁）/ I9 关闭态逐条一致（等价性回归测试以改造前算法的照抄模拟为基线快照）/ I11 双约束取更严（保留段须同时满足条数与预算两上限）/ I12 驱逐单一出口（token 与条数共用同一条 digest 路径，不新增摘要格式、不新增 LLM 调用）/ 步骤 D 兜底（尾部一组自身超预算时保留最近一组，不裁空不抛；钉住致软超只告警不迭代，保终止性）。
- **实测数字**（层 1 合成夹具，`ToolAgentRunnerTokenBudgetTest` 全 10 案）：条数窗 100 永不触发时 budget=2000 仍逐轮驱逐（"条数未超但 token 超"痛点被补上）；钉住不可驱逐走软超告警且**不迭代**（5 轮视图数锁定终止性）；计量日志开启态每轮 generate 前恰一条、关闭态零新增。估算 vs 端点真实值校准误差（peakEst vs peakReal）、长跑撑爆窗口对照（11 轮探索 A 组复现超窗 / D 组零 400）：`PENDING（缺：真模型四组对照，后置 InkHub 实测轮）`。
- **可主张点**：预算与条数是**正交双约束**而非替代——既有 `memoryWindow` 语义一行为不改；每轮「上下文计量」行与 `LoggingModel` 真实 token 透出配对，形成估算式（`WEIGHT_OTHER` 等权重）可持续校准回路；token 切点同样必须过「回退到非工具结果」唯一防线，配对协议不破坏。
- **代价**：pinned 对不可驱逐使预算只能是**软约束**（钉住内容大时必然软超，只能告警观测）；估算偏保守会把本可留窗的消息提前压进摘要（信息折损换安全边际）；无真 tokenizer（分词表随模型而异），校准存在残余误差，需靠层 2 实测持续回调权重。

## 条目 3：回捞通道由框架两级自带，使上下文治理对业务零侵入（`RunScopedRecallBuffer`，修正案 A10）

- **问题**：L1 的卸载/句柄/回捞三件事原以「listener 提供会话事件流回捞」为前置（旧 I5：`supportsToolResultRecall()==true` 才卸载）。后果是治理收益只覆盖会话链——一次性批处理链（如 `SmartQueryMaintainService`、`SmartAgentAssetGenerateService` 的裸 `new AgentLoopListener(){}`）**即使运维持了开关也一动不动**：既不卸载也不注册回捞工具，超窗照旧撑、驱逐照旧丢，且从日志上看不出"没生效"的原因。
- **现有方案缺陷**：①把"有没有取回路径"这件事交给业务实现，等于把治理的可用性写成接入进度，越是长尾链路越享受不到；②若只把工具注册改成恒真而不补通道，模型调上来必捞空（半开态，比不注册更坏，正是 I15 禁的形态）；③社区常见的"记忆即 tool"（agent 自主 add/search）解决不了此问题——裁剪必须无条件发生，不能等模型想起来。
- **本机制不变式**：**I16** ①只存"对模型不可见者"（入场被卸载为指针的、被窗口驱逐进摘要的），窗内可见原文与收口保原文（I10）一律不入表 ⇒ 不与窗口内容重复付费；②生命周期严格等于一次 `run()`（随 `RunStats` 局部变量释放，runner 无实例字段守 I14），绝不跨 run 引用、绝不被业务持有；③只读回捞，绝不写会话事件流（不破 I13 单写者）。取数次序**事件流优先、缓冲兜底** ⇒ 会话链行为与引入本类之前逐字一致；事件流若返回指针文本视为 miss（杜绝"捞→又是指针"二次回路）。开启判据随之简化为 `recallUsable = offloadChars>0 || tokenBudget>0`（I15 同源刀不变，只是不再叠通道位）。
- **实测数字**（层 1 合成夹具）：轻链路（`supportsToolResultRecall` 取接口默认 false）端到端——1 万字报告被卸载为指针、`recallToolResult` 经 run 缓冲取回**逐字符等于原文**（`ToolAgentRunnerOffloadTest#轻链路无事件流同样卸载并注册回捞工具且可取回原文`）；轻链路 token 驱逐路径同样成立（`ToolAgentRunnerTokenBudgetTest#轻链路digest句柄端到端回捞逐字符等于原文`）；真值矩阵 6 格中两格随 A10 由 false 改判 true，其余四格锁 I9/I15 不破（矩阵本身即"不半开"的回归闸）。缓冲容量单测锁 FIFO 挤出与"未找到"表述（`AgentToolRecallTest`，4 案）。llm 模块 `Tests run: 129, Failures: 0`（权威 `TEST-TestSuite.xml`，A10 净 +5 案）。
- **可主张点**：**治理收益的覆盖面从"接入会话链的链路"扩到"任何走 `ToolAgentRunner` 的链路"，业务侧零代码**——开关一置正值即生效；同时"默认注册工具"不是孤立动作而是通道自带的必然结果，故不存在有工具无数据/有句柄无工具的半开窗口；跨 run 与 run 内的差别被显式建模为一个能力位（`supportsToolResultRecall` 只决定可捞范围），而不是一个开关。
- **代价**：①run 期间原文在堆里多驻留一份，上限由 `AGENT_TOOL_RECALL_BUFFER_CHARS`（默认 120000 字）FIFO 挤出封顶——**长 run 累积的不可见原文可远超窗口**，不设上限即无界堆占用；被挤出的句柄回捞返回"未找到（已被容量挤出）"，即"无损"承诺在极端长跑下退化为有界退化（`dropped()` 可观测）；②裸链路的"可回捞"范围仅本次 run——将来若有人把裸链改造成多 run 复用同一消息历史，必须同时接通道，否则上一 run 的句柄必失联（此约束写在 I16 类注释，属可预见的误用点）；③会话链多算一次 `LinkedHashMap` 存取消除不了（事件流优先，故只是常数级开销）。
