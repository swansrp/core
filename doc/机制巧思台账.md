# 机制巧思台账

> 定位：登记共享框架（`core/*`）中「巧思型」机制的设计动机与实测证据，防止后来者不知然否地改坏。
> 每条严格六要素：**问题 / 现有方案缺陷 / 本机制不变式 / 实测数字 / 可主张点 / 代价**。
> 实测数字口径：层 1 = 合成夹具（`ScriptedModel` 假模型 + `ContextProbeTools` 30k 中文报告 + `KEY-*` 深藏探针，确定可复现）；层 2 = 真模型四组对照（A 基线 / B 仅卸载 / C 仅预算 / D 双开）。

---

## 条目 1：工具结果入场卸载 + 句柄回捞（`toolResultOffloadChars` + `recallToolResult`）

- **问题**：多轮工具探索里，一条超大工具结果（如 30k 字的解析报告）全文进入消息窗口后，**每一轮后续请求都重付这笔 token**；滑动窗口只在驱逐时才摘要，救不了"还在窗内的每一轮"；模型输入爆炸且成本失控。
- **现有方案缺陷**：①条数窗口（`memoryWindow`）对"一条巨大结果"完全无感知——1 条 30k 与 1 条 50 字同计 1 条；②驱逐摘要（`digestOf`）发生在**被裁掉的那一刻**，此前每轮都已为全文付费；③若只做截断不留出处，模型丢信息后要么瞎猜要么重复调用原工具（同参重调在 `cachedTools` 下仍是全文照付）。
- **本机制不变式**：I1 配对完整（卸载只换文本不动结构）/ I2 顺序与类型不变 / I4 事件流全文是真源、回捞零损失 / I5 卸载必有取回路径（A10 起由框架两级通道保证：run 缓冲兜底 + 会话事件流优先，不再以链路能力位为前置）/ I6 钉住 ∪ askUser ∪ recallToolResult 永不卸载、回捞结果不二次卸载 / I7 句柄落在指针首行前 60 字符内，经任何 `brief` 截断仍可回捞 / I10 收口路径一律原文 / I15 摘要行内句柄与回捞工具注册同源（`recallUsable` 一布尔定生死，默认全关时二者皆无）。
- **实测数字**（层 1 合成夹具，`ToolAgentRunnerTokenBudgetTest#层1对照数字表`）：入窗峰值字符 **120100 → 24859**（D 组含三次回捞仍降 ~79%）；三处深藏探针 `KEY-A/B/C-8888`（位于 30k 原文 60% 偏移，头尾预览不可见）经句柄回捞**逐字符命中 3/3**；askUser 口径经钉住在末轮入窗存活；`cachedTools` 命中路径配新句柄可再回捞（`ToolAgentRunnerOffloadTest`）。
  **层 2 真模型对照（已补，InkHub `inkhub-check` 同题长程链路 2026-09-25，取证与测量口径见 `docs/poc/context-gov/README.md`）**：
  ① **修 I7 缺陷前实测收益为 0**——生产 `tool_call_id` 是 29 字 `call_<24hex>`，旧 `pointerOf` 那道 `first.length() >= 100` 恒成立 ⇒ 真链路 `累计卸载` 全程 0（变更日志第四笔），层 1 短 id 用例从未覆盖此维度；
  ② 修后**等轮次前缀对照**（A 全关 / B 仅卸载 off=2000，各取前 43 次 LLM 调用，两组各自 `windowClean=true` 自证无并发）：累计 prompt **866,003 → 698,175（−19.4%）**、单轮均值 20,140 → 16,237、**peakReal 31,014 → 23,617**、末 10 轮稳态 **28,038 → 17,312（−38.2%）**；
  ③ 🔴 **全 run 口径推翻"卸载省总量"（本轮二次改判，先前写过的"轮次变化 = 0"是把中途快照当终局）**：
  三方核对口径（见条目 2 ⑦ 的「口径正源」）得全 run 总账——关闭态 **48 轮 / 1,032,371**，仅卸载 **68 轮 / 1,027,481**
  ⇒ **单轮均值 −29.7%、末 10 轮稳态 −58.2%、峰值 −31.0%，但总量打平（−0.5%）**。
  即"**每轮载荷 ↓ ⇄ 轮次 ↑ ⇒ 总量守恒**"这条规律在本形态（长深读＋大量有界等待＋载荷被钉住）成立
  （该腿 43 轮时点确实与 A 持平，收口时却多出 20 轮；两腿各 n=1，轮次差能否归因卸载，层 3 已答：**不可归因**，见 ⑦′）。
  ⇒ 本机制的**可主张面在"峰值不炸＋稳态不爬坡"（可行性与长会话下限）之外，层 3 补回一格真总量收益**：
  严格等轮次的小用例（117 次文档抓取结果逐轮重付、全部在卸载射程内）实测**总量 −15.6%、峰值 −55%** ⇒
  **载荷落在射程内且被逐轮重付时卸载确实降总量**；载荷大头被 `pinnedTools` 挡住时才只剩峰值与稳态收益。
  **而预算档（条目 2）改写轮次更猛**（×3.1，条目 2 ⑥）。
  ④ 爬坡曲线对照：A 组每 8 调用均值 8,535→14,334→20,010→27,291→26,776→30,143（单调爬），B 组 7,814→13,952→19,536→21,924→**17,963→16,226**（第 4 块掉头，卸载集中生效后压平）；
  ⑤ 真实回捞分布：3 次命中（各回填 ~2.5k 字原文，指针→全文零损失）+ 第 4 次触 `AGENT_TOOL_RECALL_MAX_PER_RUN=3` 被拒并收到收口指令——**额度在开场 1 分钟内被花完**，是"有界最坏成本"生效的实证，也是上限调参（拟 5 次/每句柄至多一次）的依据；
  ⑥ 卸载命中 11 次 / 回收 14,474 字（阈值 2000；命中集=search_docs / grep_document / fetch_document / queryExternalTask 四类长结果）。
- **可主张点**：模型侧近零信息损失（可回捞、句柄可指针化再被摘要搬运仍完整）、人工侧零损失（事件流全文照旧、前端过程树可展开）；窗内指针被裁进摘要后句柄仍随行保留（I7 贯穿截断 + I15 贯穿驱逐，全程无失联点）；不新建表、不新建缓存、不新建端点——回捞只读现成会话事件流（I13 单写者不破）。
- **代价**：多一个内建工具 `recallToolResult` 进 specs（仅开启态注册，默认关零足迹）；Redis 写失败时事件流缺原文、跨 run 回捞可能落空（A10 起本 run 仍有缓冲兜底，返回"未找到句柄+可用清单"指令，模型按预览保守作答）；事件流存储量不因卸载下降（只压模型输入）；"何时必须回捞、何时预览够用"的判断责任落在提示词（指针尾行明令禁止凭预览猜测）；**摘要行每挂一个句柄多占约 30-40 字符**（真实 `tool_call_id` 长度），而摘要总长封顶 `DIGEST_MAX_LEN=3000`，故同容量下可留存的探索条数下降——换来的是被裁内容从"永久失联"变为"可按句柄取回"（I15）；**`pinnedTools` 与卸载阈值互斥（层 2 实测的边界，消费侧最容易踩空的一格）**：钉住集按 I6 免疫卸载，故"最大宗的超长结果若恰在钉住集内，治理一分收益都吃不到"——InkHub 实测形态里 `waitExternalTask` 的 16 条 RUNNING 快照共 23,128 字（其中 7 条超 2000 字阈值）全数被钉住挡下，占该形态总结果量的 28%，把 wait 摘出钉住集（保留 `readExternalTaskResult`）才能吃到这一宗，而它属消费侧参数裁定不是机制缺陷；同一枚硬币的另一面是**阈值取值无固定最优档**（4000 字建议档在 wait 主路径形态下只命中 3 条 / 17%，2000 字命中 11 条 / 46%），开启前须按消费方结果尺寸分布实测（`docs/poc/context-gov/digest.mjs` 口径）；**离线用例的 id 形态维度**：短 id（`call-1`）用例全绿曾长期掩盖生产 29 字 id 的零卸载缺陷，任何触碰指针格式的改动必须同时带长 id 与畸形超长 id 两个用例（`ToolResultOffloaderTest` 已钉死）。

## 条目 2：裁窗计量单位从条数补上 token 预算（`contextTokenBudget`）

- **问题**：滑动窗口以「条」为唯一量纲，防的是消息**条数**堆积；但决定成本与端点上限的是 **token**——"20 条短消息"与"20 条含数万 token 大结果"获得同等待遇，既压不住爆炸也误伤精简长程探索。
- **现有方案缺陷**：①条数维度对 token 量纲两个方向都错（大结果占不满条数配额却撑爆上下文；小结果条数超了却远未到成本/上限）；②无估算回路则无从校准，真实 `inputTokenCount` 只在事后日志里出现。
- **本机制不变式**：I8 估算只高不低（CJK×1.0 + 其他×0.3 + 每消息 4 + 工具定义×1.2，宁高估早裁）/ I9 关闭态逐条一致（等价性回归测试以改造前算法的照抄模拟为基线快照）/ I11 双约束取更严（保留段须同时满足条数与预算两上限）/ I12 驱逐单一出口（token 与条数共用同一条 digest 路径，不新增摘要格式、不新增 LLM 调用）/ 步骤 D 兜底（尾部一组自身超预算时保留最近一组，不裁空不抛；钉住致软超只告警不迭代，保终止性）。
- **实测数字**（层 1 合成夹具，`ToolAgentRunnerTokenBudgetTest` 全 10 案）：条数窗 100 永不触发时 budget=2000 仍逐轮驱逐（"条数未超但 token 超"痛点被补上）；钉住不可驱逐走软超告警且**不迭代**（5 轮视图数锁定终止性）；计量日志开启态每轮 generate 前恰一条、关闭态零新增。估算 vs 端点真实值校准误差（peakEst vs peakReal）、长跑撑爆窗口对照（11 轮探索 A 组复现超窗 / D 组零 400）：
  **层 2 已补（InkHub 同题长程链路 2026-09-25，取证 `docs/poc/context-gov/README.md`）**：
  ① **估算方向与幅度（两腿 77 轮逐轮配对：计量行在前、其后 90 秒内第一条 `[AGENT-SYNC]` 即本轮端点真值）**：
  **77/77 全部 est > real、无一低估 ⇒ I8「估算只高不低」在真模型真 tokenizer 下成立**；
  仅卸载腿 43 轮平均高估 **+12.7%**（estAvg 18,305 vs realAvg 16,237，比值 0.798–0.951、中位 0.876）、
  预算腿 34 轮平均高估 **+16.0%**（estAvg 8,115 vs realAvg 6,993，比值 0.798–0.914、中位 0.863）；
  同源同轮峰值对照 peakEst 26,761/peakReal 23,617（大窗）、9,849/8,447（小窗）
  ⇒ **高估幅度随入窗变小而上升**（固定项"每消息 4 token＋工具定义×1.2"在小窗里占比更高），
  故预算键换算式取两腿上界 **`目标真实 token × 1.15`**，`WEIGHT_*` 不必回调（方向恒安全）。
  ② **预算生效面**：`bud=8000` 腿 34 轮内单轮真实入窗均值 6,993、**峰值 8,447**（= 预算线 × 1.06，余量为不可拆的工具结果组），
  同题关闭态均值 17,951、峰值 29,236，仅卸载态 15,971/23,617 ⇒ **三腿等轮次累计对照 610,347 / 543,012 / 237,751（预算腿 −61.0%）**
  （⚠️ 前 34 轮切片口径，**不得外推为整段收益**——同腿跑到收口总量反转为 +71.8%，见 ⑥）；
  ③ **双轨取严归属实测**：预算态下事件流审计行全为 `token 预算触发驱逐：保留尾部 N 条…驱逐入摘要 M 条`，
  且窗内 `条数` 恒 11–30 远低于 `memoryWindow=60` ⇒ **条数窗这一维在预算态下几乎从不触发，I11 的"取更严"确实由 token 侧胜出**（关闭态则是条数窗满载后一路爬坡至 28k+）；
  ④ **代价的实测形态**：预算腿把外部深度阅读派单从第 4 轮推到第 14 轮（窗内只留 8k ⇒ 探索记忆变薄、多绕约 10 轮）。
  此处曾按"均轮成本恒定"估出盈亏平衡 ≈138 轮并判"轮次变多不足以推翻收益"，**该模型已被 ⑥ 的收口实测推翻**
  （两个假设都不成立：均轮成本不恒定、轮次增幅无界）；**预算线低于消费方"一轮工具结果体量"时会退化为频繁驱逐**
  （驱逐强度按每轮比率算：预算腿前 34 轮 73 条＝2.1 条/轮 vs 仅卸载腿全 run 110 条/68 轮＝1.6 条/轮）；
  ⑤ **关闭态（bud=0）真环境零足迹实测**：A 腿 48 轮全程无「上下文计量」行、`累计卸载=0`、事件流 `tool_result` 载荷无指针串——即治理关闭时不新增日志、不改动消息、不留下任何痕迹。
  （注：与改造前算法"逐条一致"的等价性是层 1 的 I9 回归案所证，真环境这一层只测到"零足迹"，不外推为已复现等价性。）
  ⑥ 🔴 **全 run 反转（本条目最重要的层 2 结论，等轮次切片不可外推为整段收益）**：同一腿跑到收口是
  **149 次调用 / prompt 1,773,332（三方核对口径；事件流只数到 146 行＝缺 3 条每轮 token 审计行）**，对比关闭态 48 次 / 1,032,371 ⇒ **单轮均值 −44.7% 而总量 +71.8%，净亏**，
  且第 120 探索轮触 `工具探索达上限` 被强制收口。三条实测证据构成负反馈环：
  (a) 重复取证爆炸——`grep_document`×58 / `fetch_document`×52，是关闭态（20/11）的 2.9×／4.7×；
  (b) **回捞出口被额度堵死**——`recallToolResult` 11 次调用仅前 3 次命中（额度 per-run 计数、先自增后判），
      其后 8 次横跨 seq 136→1011 全被拒，模型被拒后不保守作答而转全量重查 ⇒
      **预算越紧 ⇒ 越依赖回捞 ⇒ 越快耗尽额度 ⇒ 重复取证 ⇒ 轮次与驱逐再涨**（`累计驱逐=375` vs 仅卸载腿 110）；
  (c) **预算线被钉住累积击穿**——末段 `条数=75 字符=19,271 估算token=14,947`，`memoryWindow=60` 早已越过但
      钉住项免疫驱逐（I6 软超告警），每 8 调用均值 5,895→…→8,423（第 6 段）→14,612 起一路 14.5k 平台，
      **预算实际只守住前 ~56 轮**。
  由此得两条**参数耦合硬约束**（详见策略文档 §六.1）：开预算档前必须先放宽回捞额度、先把长等待类工具摘出钉住集，
  否则本机制在"轮次已被长轮询压得很低、每轮很重"的形态下是**负收益**。
  质量侧不受损：三腿终局对题目所问（逐字摘录四款＋附录五行页码）**全等**，预算腿甚至最全。
  ⑦ 🔴 **跨机制结论＝"每轮载荷 ↓ ⇄ 轮次 ↑ ⇒ 全 run 总量守恒"（层 2 落点；🔴 层 3 已把它从"普适"收窄为"形态相关"，见 ⑦′）**：
  全 run 三方核对总账 关闭态 48 轮 1,032,371／仅卸载 68 轮 1,027,481（**−0.5% 打平**）／卸载＋预算 149 轮 1,773,332（**+71.8%**）。
  ⇒ 上下文治理**不具备"降低任务总成本"的能力**，它买到的是峰值与稳态斜率（可行性、长会话下限）；
  判据由此清晰：**只有减少轮次（消费侧有界等待那一类）才减少总量**。
  ⑦′ 🔴 **层 3 归因实验（同臂各重复 3 次的小用例）改判两条**（取证 `docs/poc/context-gov/README.md`「层 3 归因实验」节）：
  (a) **轮次差不可归因于治理，且该实验设计自带天花板**——OFF/ON 两臂五腿全被 `maxExploreRounds` 钉在同一轮数＝**删截**，
  上限之下的轮次差异根本测不出；⇒ **框架侧凡要测"某配置是否改写轮次"，必须先把探索上限抬到题目能自然收口之外**（方法论前提，比结论更耐用）；
  (b) **守恒律是形态相关**——严格等轮次的一对（121 vs 121）实测卸载**总量 −15.6%、峰值 −55%**，因该题 117 次文档抓取结果
  逐轮重付且全部在卸载射程内 ⇒ ⑦ 的"打平"只适用于载荷大头被 `pinnedTools` 挡住的形态（本条三腿即此类）。
  配套的可复用口径（🔴 层 3 后由"单口径"升级为**三方核对**）：`LoggingModel` 每轮向会话事件流上报的真实 input token
  按 `seq` 去重求和只是三条互证之一——它**免并发不免丢行**（小用例实测每会话缺 0～34 行，缺行即系统性低估，
  本条 ⑥ 的"146 次 / 1,730,590"就是这样被当成真值过一次）；须与①会话侧 `LLM 第 N 轮` 最大 N、
  ③共享日志该窗内 `[AGENT-SYNC]` 条数（该行不含 sessionId）互证：**①==③ 取③，①≠③ 退回②并标"下界"**。
  框架后续做"单会话 token 上界/计费"**不能只读事件流**，且"审计行为何在长会话中不成对"是**框架候选缺陷**（层 3 只测出现象、未定位根因）。
  完整口径规则另见策略文档 §六.1「口径正源」。
- **可主张点**：预算与条数是**正交双约束**而非替代——既有 `memoryWindow` 语义一行为不改；每轮「上下文计量」行与 `LoggingModel` 真实 token 透出配对，形成估算式（`WEIGHT_OTHER` 等权重）可持续校准回路；token 切点同样必须过「回退到非工具结果」唯一防线，配对协议不破坏。
- **代价**：pinned 对不可驱逐使预算只能是**软约束**（钉住内容大时必然软超，只能告警观测）——层 2 实测把这一软肋的形态钉死：**长等待类工具进了钉住集时，其快照在窗内累积可把预算线整体顶穿**（InkHub 实测末段估算 14,947 vs 预算 8,000，预算只守住前 ~56 轮），且预算档与回捞额度**耦合**——窗越薄模型越想回捞原文，额度（per-run 计数、先自增后判）耗尽后即转向全量重复取证，**激进档在"轮次已被长轮询压低、每轮很重"的形态下净亏（实测总量 +71.8%）**，两条前置动作见上 ⑥ 与策略文档 §六.1；估算偏保守会把本可留窗的消息提前压进摘要（信息折损换安全边际）；无真 tokenizer（分词表随模型而异），校准存在残余误差，需靠层 2 实测持续回调权重（两腿 77 轮配对：高估 +12.7%～+16.0%，**入窗越小高估越大**，故换算式取 ×1.15 上界）。

## 条目 3：回捞通道由框架两级自带，使上下文治理对业务零侵入（`RunScopedRecallBuffer`，修正案 A10）

- **问题**：L1 的卸载/句柄/回捞三件事原以「listener 提供会话事件流回捞」为前置（旧 I5：`supportsToolResultRecall()==true` 才卸载）。后果是治理收益只覆盖会话链——一次性批处理链（如 `SmartQueryMaintainService`、`SmartAgentAssetGenerateService` 的裸 `new AgentLoopListener(){}`）**即使运维持了开关也一动不动**：既不卸载也不注册回捞工具，超窗照旧撑、驱逐照旧丢，且从日志上看不出"没生效"的原因。
- **现有方案缺陷**：①把"有没有取回路径"这件事交给业务实现，等于把治理的可用性写成接入进度，越是长尾链路越享受不到；②若只把工具注册改成恒真而不补通道，模型调上来必捞空（半开态，比不注册更坏，正是 I15 禁的形态）；③社区常见的"记忆即 tool"（agent 自主 add/search）解决不了此问题——裁剪必须无条件发生，不能等模型想起来。
- **本机制不变式**：**I16** ①只存"对模型不可见者"（入场被卸载为指针的、被窗口驱逐进摘要的），窗内可见原文与收口保原文（I10）一律不入表 ⇒ 不与窗口内容重复付费；②生命周期严格等于一次 `run()`（随 `RunStats` 局部变量释放，runner 无实例字段守 I14），绝不跨 run 引用、绝不被业务持有；③只读回捞，绝不写会话事件流（不破 I13 单写者）。取数次序**事件流优先、缓冲兜底** ⇒ 会话链行为与引入本类之前逐字一致；事件流若返回指针文本视为 miss（杜绝"捞→又是指针"二次回路）。开启判据随之简化为 `recallUsable = offloadChars>0 || tokenBudget>0`（I15 同源刀不变，只是不再叠通道位）。
- **实测数字**（层 1 合成夹具）：轻链路（`supportsToolResultRecall` 取接口默认 false）端到端——1 万字报告被卸载为指针、`recallToolResult` 经 run 缓冲取回**逐字符等于原文**（`ToolAgentRunnerOffloadTest#轻链路无事件流同样卸载并注册回捞工具且可取回原文`）；轻链路 token 驱逐路径同样成立（`ToolAgentRunnerTokenBudgetTest#轻链路digest句柄端到端回捞逐字符等于原文`）；真值矩阵 6 格中两格随 A10 由 false 改判 true，其余四格锁 I9/I15 不破（矩阵本身即"不半开"的回归闸）。缓冲容量单测锁 FIFO 挤出与"未找到"表述（`AgentToolRecallTest`，4 案）。llm 模块 `Tests run: 129, Failures: 0`（权威 `TEST-TestSuite.xml`，A10 净 +5 案）。
- **可主张点**：**治理收益的覆盖面从"接入会话链的链路"扩到"任何走 `ToolAgentRunner` 的链路"，业务侧零代码**——开关一置正值即生效；同时"默认注册工具"不是孤立动作而是通道自带的必然结果，故不存在有工具无数据/有句柄无工具的半开窗口；跨 run 与 run 内的差别被显式建模为一个能力位（`supportsToolResultRecall` 只决定可捞范围），而不是一个开关。
- **代价**：①run 期间原文在堆里多驻留一份，上限由 `AGENT_TOOL_RECALL_BUFFER_CHARS`（默认 120000 字）FIFO 挤出封顶——**长 run 累积的不可见原文可远超窗口**，不设上限即无界堆占用；被挤出的句柄回捞返回"未找到（已被容量挤出）"，即"无损"承诺在极端长跑下退化为有界退化（`dropped()` 可观测）；②裸链路的"可回捞"范围仅本次 run——将来若有人把裸链改造成多 run 复用同一消息历史，必须同时接通道，否则上一 run 的句柄必失联（此约束写在 I16 类注释，属可预见的误用点）；③会话链多算一次 `LinkedHashMap` 存取消除不了（事件流优先，故只是常数级开销）。

## 条目 4：透视度量「比率(加权)」聚合（`agg=ratio`，`sum(分子)/nullif(sum(分母),0)`）

- **问题**：透视的度量聚合从来只能作用于"列"（六种 agg 全是单参数聚合），而"两个聚合结果之比"没有落点——加权水平分 Σ(阶段比例×标准分)/Σ(阶段比例) 这类比值口径在透视上拼不出来，消费方只能二选一：退回简单均值（口径失真：5% 可研与 40% 初设同权），或把聚合写死进 dataset 薄层（丢掉"宽表 + 请求级自由聚合"形态，每换口径重配一层）。
- **现有方案缺陷**：①除法是聚合**之间**的运算，度量表达式层没有它的位置；②条件聚合的 case when 必须**同时**包住分子与分母——手拼极易漏包一边，分母掺入其他分组的行（sum 全表比例）得出系统性偏小的加权值，且不报错、难以察觉。
- **本机制不变式**：①ratio 单元格恒为 `sum(分子)/nullif(sum(分母),0)`，分母 0 或空组回落 NULL（前端空单元格，不炸不显示 0）；②有透视条件时分子、分母**各自独立**套同一 case when（else null，聚合自动忽略，漏包一边即口径错误）；③分子/分母与普通度量字段同走别名映射与列权限校验（收窄时未命中即拒），`field` 退化为纯输出别名、单独过字符集校验堵反引号逃逸；④ratio **不可二次聚合**（前端合计/跨列小计留空，同 avg/countDistinct 待遇，禁止把比值当可加数求和）。
- **实测数字**（2026-10-08，erp 考核榜场景，Doris 真数）：2025 年明细 6,708 行守恒（总 25,248）；专业负责人榜 Top10 加权 vs 简单均值重合 10/10、最大差 2.80 分（头部重叠≠口径等价，中尾部差距更大）；带透视列形态（pmpLevel='A' 单元格）双腿 case when 数值正确；kernel/forge 定向编译过，前端 eslint/vue-tsc 净。
- 🔴 **10-09 更正（本条不变式曾被生成通道违反）**：上一条"双腿 case when 数值正确"来自**手写 SQL 重放**，只证明形态可用，不证明 forge 通道可用——`DriverStatisticSupportService.pivot` 的 ratio 分支实装成两腿**裸 CASE WHEN 相除**（两腿都没进聚合函数），页面一配 ratio 即 Doris 1105 `select list expression not produced by aggregation output (missing from GROUP BY clause?)`，且当时 forge/kernel 无任何 ratio 测试，故整条通道带病交付。已改为 `sum(分子腿)/nullif(sum(分母腿),0)`（与 kernel 形态逐字对齐），新增 `DriverStatisticPivotRatioTest` 4 案（正解正则＋两条故障形态负向腿＋无条件退化形态＋缺分子拒绝），并做 Doris 只读 A/B 回放：旧形态逐字复现用户报的 1105，新形态返回 8 行（Top 加权 90.0000／88.8900…）。**教训：不变式写进台账不会自己守住代码，机制交付须带"断言产物 SQL"的单测；手写重放只能验形态、不能验通道。**
- **可主张点**：比值类口径进透视**零 SQL、零新端点**（配置面板选分子/分母两列即成）；kernel 矩阵与 forge 动态数据集两条生成通道语义对齐；列权限不因新通道开洞（分子/分母都在收窄校验射程内）。
- **代价**：①"分子"若是乘积须预乘落列（宽表加 `propStdScore = phase_prop×std_score`），比值组合爆发时宽表列数线性涨（当前仅 1 列，未见膨胀）；②ratio 行合计留空是**语义正确**但用户可能当 bug 报（文案/文档要讲清"比值不可加"）；③前后端须同版部署——老后端收到 ratio 配置会在查询时以"未知列"报错（无 ratio 语义、也不走新校验），不炸配置炸查询。

## 条目 5：Dataset 常驻过滤谓词（`sys_dataset.base_filter`，行删除谓词的配置化）

- **问题**：dataset 贴入 SQL 的**外层 WHERE 被 `parseSql` 整段丢弃**（只登记 FROM/JOIN 表与 SELECT 列——这是丢弃的机制根源），而快照锁（`dy = 最新批次`）、软删标记这类**行删除谓词**最常被作者写在外层 WHERE。单分区数据下丢弃完全隐形（对账数字照常相等），新分区落库当天行数膨胀 3.63 倍（实测）。上一轮对策是文档约定"把锁写进 FROM 子查询"——约定不是机制：每个 join 子查询要各写一遍、写漏写错位置零告警（demo SQL 里就真实漏过一处 prj 锁，行数 91,757 vs 25,248）。
- **现有方案缺陷**：①外层 WHERE 无落库位置，丢弃无告警；②FROM 子查询锁是手艺活，N 个表 N 遍且口径漂移无从发现；③没有统一存放"行删除谓词"的位置，行权限（主体隔离）、列筛选（用户选择）、行删除（作者锁定）三种语义混在条件层拼。
- **本机制不变式**：① base_filter **只存谓词片段**（WHERE 片段），保存期六重校验（注释/分号/GROUP BY 族子句/引号外 `${}`/残缺 `${`/严格语法解析）+ token 白名单（日期变量与 `now:pattern`；主体类变量拒收——那是行权限的领地）；②运行期恒以 `(base) AND (req)` 拼接，token 整体替换为 `:param_N` **命名参数绑定**（绝不字符串替换），纯数字解析值按整型绑定；③base_filter 只进**预览构建器**（内层），外层条件构建器不带——避免重复拼接；④预览参数**先并入执行参数再构建外层条件**（`param_N` 按 map.size() 分配，任何一处顺序颠倒必碰撞——5 处统计点同一 hoist 形态）；⑤null/空归一化为 null；清除必须显式 `set(null)`（`updateById` 跳过 null 字段）；⑥base_filter=null 时生成 SQL **逐字节不变**（零行为变更是硬门槛）；⑦`${maxOf:<列>}`（按列最大值锁定）**显式延后未做**——需要查询期子查询求值，当前场景无此需求。
- **实测数字**（2026-10-08，harness 真调 parseSql→builder→context + Doris 只读回放）：校验套件 24/24（含宽松模式漏放 `x = = 1`、残缺 token `'${currentYear'` 两个被严格模式/残缺检查堵住的对照）；零行为变更 diff 逐字节为空（99 列宽表 + demo 两份）；base_filter 形态 25,248 ＝ FROM 子查询锁形态；多分区 `dim_pm_project_dyf` 过滤 16,035→5,091（当前年分区）；**共存** `{param_0=2026(base)＋param_1=2025(外层条件)}` 双过滤 6,708 行守恒（=assessYear 2025 已知行数）。
- **可主张点**：作者写错位置从"静默错数"变"保存期报错"（六重校验全在入库前）；dy 锁从 SQL 手艺升级为配置字段，作者不碰 SQL 也能锁批次；**有意不保留外层 WHERE**（丢弃即防线——避免年份等易变值硬编码进 SQL，业务默认年份留在条件/筛选层）；不新建端点、不加 sql_mode、不改既有 SQL 行为。
- **代价**：①base_filter 引用列必须在 dataset **顶层 FROM 作用域可见**——主表是派生子查询时要么把列投影出来、要么锁留子查询内（实测 `Unknown column 'dy' in 'd'`）；②多表 dataset 须带表别名前缀（顶层 WHERE 无限定歧义即炸）；③严格语法解析拒 Doris 的 `<=>`（保存期报错可改写为 OR-IS NULL 形态，好过查询期炸）；④每次查询多一次 `sys_dataset` 读取（getSqlBuilder）；⑤升级 DDL（v1）随启动自动执行——**2026-10-09 已在 dev 真库执行过**（`sys_dataset` 实测有 `base_filter` 列，id=14 `assessStdDataset` 存着 `d.dy = '${currentYear}'`）；⑥🔴 **撤销独立输入框后，"外层 WHERE 是唯一书写入口"就要求回显与保存同源**：`/dataset/sql` 必须把 `baseFilter` 随 SQL 一起下发，前端拼回末尾。第一版拼回读的是列表接口的 `ds.baseFilter`，而列表 VO 没这字段 ⇒ 恒 undefined ⇒ WHERE 不显示，且**下一次保存会命中"SQL 无 WHERE＋提交空串"的清除分支把已存常驻条件静默置 NULL**（10-09 用户实测报出后修复）。凡是"把输入框并进主编辑面"的改造，都要逐条问：这个字段的**读**通道还在不在？读不到时再写一次会不会清掉它？
