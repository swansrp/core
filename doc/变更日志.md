## 2026-09-25（第二笔）摘要行内句柄：被驱逐的工具结果从"失联"变为"可回捞"（`I15`，修正案 A9）

**状态：随本笔提交入库（本地 commit，未 push）**。承接上一笔 commit `6949a7f1`，独立成笔。

### 补的缺口
`digestOf` 生成的探索摘要行原本只留 `· 工具名(参数摘要) → 结果摘要`，**丢掉了 `tool_call_id`**。而回捞取数走 `AgentSessionContext.recallToolResult` 按 id 扫全部 TOOL_RESULT 事件、**与是否曾卸载无关**——即原文一条没少地躺在事件流里，只是句柄在裁切那一刻丢了。净效果是"窗内指针可回捞、裁进摘要即永久失联"，一个纯加法就能收口的缺口。

### Changed
- `ToolAgentRunner.java` —— ① 新增同源判据 `recallUsable = recallAvailable && (offloadOn || tokenBudget > 0)`，回捞工具注册（原条件 `offloadOn`）与摘要写句柄共用；② `digestOf` 加 `withHandles` 形参，命中工具结果的行尾追加 `（句柄=<tool_call_id>）`；③ 摘要头部在 `DIGEST_PREFIX` 之后、正文之前插一行回捞指引 `DIGEST_RECALL_GUIDANCE`，重拼时幂等剥离防重复（`DIGEST_PREFIX` 常量本身一字未动——它是关闭态也走的头部识别标记）。
- `AgentToolRecall.java` —— `@Tool` description 与 `@P` 参数说明扩到两个句柄来源（指针首行 `tool_call_id=` / 摘要行内 `句柄=`），"一次一个、禁止重复拉同一句柄"纪律措辞保留。
- `doc/Agent循环治理策略.md` §二 11/12、`doc/机制巧思台账.md` 条目 1（不变式补 I15、可主张点与代价栏更新）、`llm/README.md` §7.3（L1 注释块补"句柄双来源 + recallUsable 同源、无半开态"）。

### Impact
- **I9 未受影响**：默认全关（`offloadChars=0 && tokenBudget=0`）时 `recallUsable=false` → specs 不增工具、digest 不写句柄、无指引行，逐字符与改造前一致；照抄 HEAD 算法的基线模拟回归案**一行未改仍通过**（测试文件 183 行纯新增、零删除）。
- 新开启形态：`AGENT_CONTEXT_TOKEN_BUDGET` 单开（不开卸载）即可让被裁内容可回捞——这是本笔的实际收益面。
- 代价：摘要行每挂一个句柄多占约 30-40 字符，挤压 `DIGEST_MAX_LEN=3000` 容量 → 同容量下可留存条数下降；模型可回捞的对象变多，由 `AGENT_TOOL_RECALL_MAX_PER_RUN`（默认 3）兜住。
- 验证：`mvn test -pl framework/core/llm -am` → llm 模块 **`Tests run: 124, Failures: 0, Errors: 0`**（权威 `TEST-TestSuite.xml` 07:06:13，逐类求和一致；较上笔 +4：`ToolAgentRunnerTokenBudgetTest` 10→13、`AgentToolRecallTest` 3→4）。新增四案：`recallUsable真值矩阵specs与digest同源`（6 格断言两处同源）、`多轮驱逐指令行唯一且各行带句柄`、`摘要内指针保留句柄可回捞`、`digest行内句柄端到端回捞逐字符等于原文`（本笔存在理由：不卸载→被裁→读句柄→取回全文逐字符相等）。
- 管线：**本笔未走 Plan-Checker / Reviewer 全回环**（用户 2026-09-25 定口径：缺口修复以文档说明收口，不再起一轮审查）。理由与担保：改动面是单点加法（一个判据 + 一个形参 + 一行指引），无重构、无签名变更、无新增存储；关闭态等价由"测试文件纯新增零删除 + HEAD 基线模拟案未改仍绿"担保；开启态正确性由端到端逐字符回捞案担保。process 记录见 `.qoder/dev-logs/20260925-001020-llm上下文预算治理/session-log.md` 追加笔。

## 2026-09-25（第三笔）回捞通道由框架两级自带：治理对业务零侵入（`I16`，修正案 A10）

**状态：随本笔提交入库（本地 commit，未 push）**。承接 `ee245120`，独立成笔。动因：用户问"回捞 tool 能不能默认注册、不用业务再写"，取证后确认注册本就是框架侧自动（`ToolAgentRunner` 内 `effectiveTools.add`），真正缺的是**通道**——裸 `new AgentLoopListener(){}` 的一次性链（`SmartQueryMaintainService`、`SmartAgentAssetGenerateService`）能力位为 false，运维开关置正值也一动不动。

### Added
- `llm/.../agent/RunScopedRecallBuffer.java` —— run 作用域兜底通道（I16）：只存"模型已看不到的原文"（被卸载为指针的 + 被驱逐进摘要的），`LinkedHashMap` 插入序 + 容量 FIFO 挤出；随 `run()` 结束释放，绝不跨 run 引用、绝不写事件流
- `LlmParam.AGENT_TOOL_RECALL_BUFFER_CHARS`（闸门键，默认 120000 字）+ `AgentContextBudget.recallBufferChars()`（走 `resolveFloor`，与既有三闸同族）
- 测试净 +5 案：`AgentToolRecallTest` 4→8（轻链路经缓冲取回、事件流优先、事件流返回指针视为 miss、容量挤出的有界退化表述）、`ToolAgentRunnerTokenBudgetTest` 13→14（轻链路 digest 句柄端到端逐字符回捞）、`ToolAgentRunnerOffloadTest` 轻链路端到端一案改写（原断言"无通道不卸载"）

### Changed
- `ToolAgentRunner.java` —— 判据 `offloadOn = offloadChars > 0`（去 `&& recallAvailable`）、`recallUsable = offloadOn || tokenBudget > 0`（I15 同源刀不变，只是不再叠通道位）；`RunStats` 以 `lossy` 缓冲替换 `offloadedHandles` 台账（I14 仍无实例字段）；卸载点与驱逐点两处归档（`archiveEvicted` 与 `digestOf` 共用同一区间与钉住跳过判据 ⇒ 归档集恒含句柄集，不半开）；入场卸载日志表述改为"已入回捞缓冲(+会话事件流)"，原表述对裸链是假话
- `ToolResultOffloader.shouldOffload(...)` —— **去掉 `recallChannelAvailable` 形参**（4 参）：该方法随 `6949a7f1` 新引入且三笔均未 push，无既有消费者；I5 语义由"无通道不卸载"升为"卸载必有取回路径（两级通道）"

### Impact
- **收益面**：卸载 / 句柄 / 回捞对**任何走 `ToolAgentRunner` 的链路**生效，业务零代码；会话链行为逐字不变（事件流优先，缓冲只是 miss 后的兜底）。
